## 讨论目的

结合近期使用反馈与下方全量 issue 索引，提出一个供维护者讨论的整体构想；开放与已关闭需求均统一记录范围、关联关系和状态：

> 将 WispPaper 逐步发展为本地优先、证据可追溯的文献研究与写作工作台，贯通「搜 → 读 → 标记 → 总结 → 引用 → 书写」，并支持「GitHub 仓库 + MCP 服务器 → 可追溯证据 → 论文草稿」的 GitHub-to-Paper 扩展路线。

本帖用于讨论产品方向、能力边界和交付顺序。已有具体需求仍由原 issue 跟踪；这里不要求一次实现整个构想，也不预设必须合并其他仓库、迁移数据库或替换 UI 技术栈。

## 1. 延续现有定位

WispPaper 已明确定位于收集、筛选、阅读和向文献提问，已有独立文献库、保存检索式、定时更新、批量筛选、单篇 / 文献库问答、笔记、自定义字段及引用跳转。

希望进一步让这些能力连续起来：用户从一个研究主题出发，筛出值得阅读的论文；精读时保存原文、批注和图表；形成有来源的总结；比较多篇证据；最后把核对过的材料组织进综述或论文草稿。

适合优先验证的用户场景是「围绕一个主题做文献调研、比较方法并撰写有依据的综述或论文段落」。以后再扩展到连接实验结果和完整稿件，避免起步就承担所有科研工具的职责。

参考现有定位：https://github.com/xuzhougeng/WispPaper/blob/main/README.md

## 2. 一个具体的连续使用场景

以「比较多篇 CAR 相关论文的构建方法」为例，题材仅用于说明一般工作流：

1. 搜索数据库、保存检索式并导入文献记录，或导入已有 PDF；针对缺 PDF 条目批量查找候选全文并下载关联，常规路径不足时可主动启用助手辅助查找。
2. 分别查看全文查找、下载、导入与文字提取进度，知道哪些记录只有链接、哪些已保存 PDF，以及文件完整可读、部分可读或提取失败。
3. 按研究标准进行 AI 辅助筛选，由用户决定是否收录。
4. 在当前工作区打开主文或补充材料，缩放查看方法、图表和图注。
5. 选中原文，保存高亮 / 批注，或添加到当前对话继续追问。
6. 生成每篇论文的结构化总结和跨论文方法比较表；结论分别关联依据与局限。
7. 点击某个结论旁的原文证据，回到正确文件、页码和片段核对。
8. 将选定的总结、证据和引用插入稿件章节，修改文字，并导出草稿与参考文献数据。

原文缺失、解析不完整或仅有摘要时，应在这条流程中持续可见，不能让用户将摘要问答误认为全文阅读。

## 2.1. 扩展路线：GitHub-to-Paper，帮助开源开发者将项目形成论文

除从文献出发，还建议支持从 GitHub 仓库出发的写作入口：用户添加一个具体仓库，并按需连接一个或多个提供数据、实验或计算能力的 MCP 服务器，逐步将软件项目、真实结果和相关文献组织成可核查的论文草稿。

目标用户包括希望为公开工具、算法、软件包或数据处理流程撰写软件论文、方法论文、基准评测或应用论文的开发者。目标是减少整理项目与实验材料的重复劳动，加快形成可审阅、可投稿的稿件；稿件适用性与录用仍由作者及出版流程决定。

### 弹窗卡片式向导：先确认方向与范式，再以 Results 为起点写作

交互采用分步弹窗卡片，每步展示「当前输入、分析依据、可编辑产物、待补充信息」，支持保存草稿、返回修改和断点继续。前一步的确认结果作为下一步输入；仓库、论文方向、创新点或 Skill 变化后，明确指出哪些后续材料需要重新生成，保留用户编辑内容。

| 卡片 | 用户操作与系统工作 | 本步保存的产物 |
| --- | --- | --- |
| 1. 仓库与 MCP 能力 | 添加仓库 URL，选择分支 / 标签 / commit；添加 MCP 服务器并发现工具。先读 README 判断仓库定位，再按需要深入文档、代码、测试与示例；区分 README 宣称、代码实现和运行验证 | 仓库定位摘要、版本快照、服务器能力清单 |
| 2. 论文方向 | 根据仓库定位及 MCP 能力推荐方向，例如 MCP 工具 / 协议应用、agent 系统、软件工具、方法 / 模型、基准评测；用户也可直接输入方向、研究问题、目标读者或目标期刊 / 会议，并修改推荐 | 经用户确认的论文方向与范围 |
| 3. Web Search 与写作范式 | 围绕已确认方向检索代表性论文，展示来源、相关性及全文可用情况；用户选择参考论文，助手读取可获取的正文，比较各篇章节、Results 小节、评测设计、基线、指标、消融、案例、图表和论证顺序 | 参考论文集、逐篇分析、带来源的写作范式矩阵及本项目框架草案 |
| 4. 创新性与证据 | 用户填写自己的项目 / 方法 / 模型创新点；也可让助手提出候选创新点，再由用户修改确认。将每个创新点映射到代码功能、相关工作差异、需要证明的论断与已有 / 缺失证据 | 创新点卡片、论断—证据矩阵、缺口清单 |
| 5. Results 优先写作 | 按确认的范式与创新点先组织 Results 小节，读取仓库已有结果或通过 MCP 获取实际证据，生成可编辑段落、图表计划和来源链接；按小节检查逻辑与证据后逐段推进 | Results 草稿、证据关联、图表说明、待完成实验 |
| 6. 后续章节与导出 | 以 Results 为依据，按用户选定顺序组织 Methods / Implementation、Discussion、Related Work / Introduction 等章节，最后汇总 Abstract；核对引用、章节一致性、来源与软件可用性后导出 | 经用户编辑的稿件、参考文献与证据清单 |

### 从参考论文提炼可追溯的写作范式

- Web Search 在确认研究方向之后开展，记录检索词、候选来源及选择理由；不能只按仓库关键词匹配就固定论文类型。
- 输出可编辑的范式矩阵：每篇论文如何提出问题、安排 Results、设置比较、组织图表和讨论局限，并关联到具体章节或原文。
- 从多篇论文归纳共性与差异，再让用户选定适合本项目的框架。参考论文的组织方式与本项目证据需要对应，不能直接复制范文或强行套用单篇结构。
- 只能访问摘要时，明确标注分析范围；检索不可用或正文不可得时，支持用户补充 DOI、PDF 或指定参考论文，并保留未完成状态。
- 用户可以在此选择 / 切换写作 Skill；范式总结与实际 Skill 约束发生冲突时，将差异展示给用户处理，保存最终采用的框架版本。

### 创新点驱动、以 Results 为起点的逻辑写作

- 支持「用户输入创新点」和「模型提出候选、用户确认」两种入口，也支持填写模型或算法本身的创新。模型提出的候选仍需对照相关工作与真实实现核实。
- 每个 Results 小节回答一个明确问题，围绕「创新点 / 论断 → 需要的证据 → 已有结果 → 图表 / 案例 → 段落结论」展开，符合前一步确认的写作框架。
- 对 MCP / agent / 软件论文，小节可能涉及系统能力、功能验证、工具互操作、任务评测、效率、基线比较、消融或案例；由论文方向与真实材料决定，不固定成统一的性能实验模板。
- 仓库中已有代码、接口或演示可支持实现与功能描述，但不能自动支持性能优越、泛化或可靠性结论。需要运行证据时，列出实验需求，经用户授权再通过具备该能力的 MCP 工具执行。
- 区分仓库说明、已实现能力、已完成测试、实际运行结果、作者设想与尚未验证的主张；真实数据缺失时保留待补证据，不生成虚构数值。
- MCP 长任务保留任务 ID、进度、失败原因和产物定位；结果绑定 commit、数据版本、参数、环境与运行记录。远端大文件可保留带校验信息的引用。
- 从任何结果段落可返回指定版本的代码文件 / 行、实际运行产物或文献原文。Results 完成后，后续章节沿用同一份创新点与证据，便于发现表述矛盾。

### 写作 Skill：与 wisp-science 无缝衔接

要求写作过程可按需调用 Skill，对论文方向判断、文献范式归纳、Results 结构、证据边界、术语与引文核对进行约束；界面显示本阶段采用的 Skill，允许用户配置与替换。

支持两类来源：

1. **wisp-science 会话沉淀的 Skill**：允许用户将已有研究 / 写作会话中整理出的有效步骤、范式和核对规则形成 Skill，预览编辑后导出给 WispPaper；也可在 WispPaper 中选择已导出的包。跨应用取用会话内容由用户选择来源和范围，保留可追溯的转换来源，不默认访问全部会话。
2. **用户自行配置的 Skill**：支持本地 Skill 目录、`SKILL.md` 或完整 ZIP 包导入，预览说明、适用方向、附带资源和依赖后用于当前写作阶段。

格式与行为兼容要求：

- 直接兼容 wisp-science 的「Skill 目录 + SKILL.md + YAML frontmatter + Markdown 正文」；保留 `name`、`description`、`tags`、`version`、合法的额外元数据与已有 `wisp` 扩展字段，按约定 schema 版本校验，避免另造不兼容格式。
- 保留 `references/`、`scripts/`、`assets/` 等相对资源及引用关系，不能只复制 SKILL.md 后丢失范式、模板或校验脚本。明确单文件导入的资源缺失情况。
- 对 `runtime.py` / `runtime.r` 等 sidecar，沿用按需加载的约定：格式可读与脚本可执行分开检查；缺少 Python / R / MCP 等能力时明确提示或提供可用替代路径，不静默跳过关键步骤。
- 优先复用或抽取 wisp-science 的 manifest 解析、校验、资源解析和按需加载规则。保存导入来源、版本 / 校验信息及本次采用的 Skill 快照，历史稿件可还原当时约束。
- 会话到 Skill 的沉淀、Skill 导入 / 调用和 Skill 到独立 Workflow 的转换是不同流程。实现时核对并衔接当前真实入口；不能用已有 Skill-to-Workflow 代码宣称已完成会话转 Skill。
- Skill 规定写作步骤与输出格式，程序校验可验证的文件、页码、引文、运行结果和来源关联；两者共同支撑核对状态。

当前已核对 wisp-science 的 manifest、导入和运行时指引代码，其格式包含上述基础；WispPaper 的写作 Skill 调用、向导及跨应用会话沉淀连接仍属于本帖提出的新能力。

### 向导与兼容性的验收建议

- 完成「添加仓库与 MCP → README 定位 → 方向确认 → Web Search / 论文范式 → 创新点确认 → Results 初稿」的一次卡片式交互，退出后可恢复。
- 用户可修改方向、参考论文、创新点和 Skill；系统保留手工编辑，并标记需要重新核对的下游结果。
- 弹窗与内层 Skill / 文献选择器支持窗口级 Escape 层级：打开后无需先点击内部，一次仅关闭最上层，保留父层及已填写内容。
- 以 wisp-science 合法 Skill 包做跨应用兼容样例，验证 YAML、扩展字段、中文路径、相对引用及资源读取；导入无需手工改写格式。再验证会话沉淀导出包与用户自备包的等价加载。
- 不支持的 schema、缺失资源、缺少运行时、Web 检索失败或 MCP 无对应工具时，提示具体限制；测试使用假搜索与假 MCP，不依赖真实账号和付费服务。
- 同一 Results 小节可以回溯参考框架、用户确认的创新点、采用的 Skill 和实际证据；未执行实验不被写成已获得结果。

### 与其他仓库的能力融合

- **WispPaper**：负责相关文献检索、精读、引用、证据组织与稿件入口。
- **wisp-science**：评估抽取执行上下文、Run 生命周期、Artifact 版本及 Publication 证据关联等已有思路，通过明确接口对接；不必把全部计算能力搬入 WispPaper。
- **ScientificFigureLibrary**：在已有真实结果基础上复用图形模板，关联所用模板版本、绘图代码与输出。
- **Typorax / CiteBox**：分别参考稿件编辑与阅读笔记的交互，承接可编辑草稿、摘录和图表说明。

### 最小可行版本

先用分步弹窗卡片实现「添加一个公开仓库的具体 commit 与一个 MCP 服务器 → README 定位与用户确认方向 → 检索代表论文并确认范式 → 确认创新点 → 加载兼容的写作 Skill → 读取已有结果 → Results 草稿与来源核对」。其后补齐其他章节和导出；会话沉淀连接、远程自动实验、复杂调度和多服务器协作分别交付与验收。

这条路线还需新增 GitHub 仓库来源管理和外部 MCP 客户端连接能力。WispPaper 当前向外暴露文献工具的 MCP 服务端，不能直接视为已经具备连接任意外部 MCP 服务器的能力。

与现有文献路线共用同一稿件与证据体系：

**相关文献 + 指定版本的仓库 + 可追溯的运行结果 → 论断与证据 → 论文草稿。**

## 2.2. 全文获取：批量补齐缺失 PDF，提供可选 AI 辅助查找

具体需求见 #32；模型辅助路径的核对结果与建议见 https://github.com/xuzhougeng/WispPaper/issues/32#issuecomment-6795753088 。

### 主要路径：明确来源的批量查找与下载

当前「检索与导入」主要导入文献记录。「有链接」可以只是 DOI 或论文页面，不代表找到可下载 PDF，也不代表全文已保存在本地。

建议在「缺 PDF」视图和检索导入完成后提供：

**选择文献 → 按标识符查找全文 → 展示候选来源与版本 → 用户选择 → 下载并关联原条目 → 提取文字 → 显示可用范围。**

- 先接入一种可验证的开放全文获取路径，再按需扩展来源；主要流程不依赖模型配置。
- 保留原条目、收录决定与已有附件，避免重复建文献；核对身份并区分预印本、作者稿、正式版本、主文和补充材料。
- 统一展示查找、候选选择、下载和提取进度，支持取消、重试与批次汇总。
- 区分「有网页链接」「找到候选 PDF」「已保存 PDF」「全文文字可读」；普通 HTML、登录页或错误响应不应被当成 PDF 保存。

### 可选路径：让助手继续查找 PDF

常规来源未找到或匹配不确定时，由用户主动选择「让助手继续查找 PDF」。助手根据 DOI、标题、作者等信息调用已配置的检索 / MCP 工具，可结合检索 Skill 核对候选，再交回统一下载与附件关联流程。

这项能力是额外辅助，不是主要功能的运行前提，也不应通过模型猜测直接生成下载地址或成功状态。模型与工具不可用时，基础查找、下载及手动附加仍可使用。

### wisp-science 可抽取的工具基础与边界

已核对的工具包括：

- `openalex_search_works` / `openalex_get_work`：文献检索和详情，结果可包含 `best_oa_pdf_url`。
- `arxiv_search` / `arxiv_get_papers`：文献记录及 `pdf_url`。
- `get_full_text_article`：获取可用的 Europe PMC 全文 XML / 文本；这与下载原始 PDF 是两类材料，需分别保存和展示。
- 通用 Python / shell：具备由模型编排 HTTP 下载的基础，但需实际具备相关网络、运行时和工具能力。

这些是可复用的候选链接发现、全文获取与执行能力，不等于 wisp-science 已提供通用的「任意论文自动下载并关联 WispPaper」完整功能。可先抽取检索结果契约与来源适配器，无需让 WispPaper 用户为基础下载安装整套计算环境。

### 与阅读、证据和写作衔接

发现或下载成功后，保存来源、获取时间、版本与校验信息，再将实际可读内容提供给单篇 / 文献库问答、阅读笔记、原文核对和写作。设置模型检索步数、时间及并发边界；不能用「已找到论文」代替「已取得并解析全文」。

验收时分别验证不配置模型的批量流程，以及假检索 / 假 MCP 驱动的可选助手流程；覆盖错误候选、无全文、非 PDF 响应、取消重试和下载后提取失败。

## 2.3. 内置论文编辑器：实时编辑、AI 修订与有明确范围的 DOCX 兼容

延续此前 wisp writing 的讨论，建议在 PR #31 已有分章节草稿基础上，评估内置论文编辑器：用户在 WispPaper 中写作或打开已有 DOCX，选中文字交给助手润色、缩写、翻译或核对，再在原位置审阅修改。文献路线和 GitHub-to-Paper 向导共用这一个稿件入口；参考文献、Results、图表与证据可以插入对应段落并保留来源。

这是一项供维护者评估的新概念，不将现有写作页等同于完整 DOCX 编辑器，也不要求把 WispPaper 做成与 Word 全面对等的排版软件。

### 参考 wisp writing：复用原生修订思路，区分已有实现与新增目标

- [wisp-science #1679](https://github.com/xuzhougeng/wisp-science/issues/1679) 提出「先标注修改，再逐条或按类型接受」；最初设想转换为 Muse，后续讨论指出 Muse 与 Word 不能完全对应，实际实现转向 DOCX 原生修订，不应把强制转 Muse 当作既定方案。
- [已合并 PR #1706](https://github.com/xuzhougeng/wisp-science/pull/1706) 引导既有 DOCX 改写走 `read_docx → suggest_docx_edit`，避免重新生成脚本覆盖文档；同时改善空修订栏及修订列表 / 文档之间的可调分隔。它没有关闭 #1679，也没有实现完整的自由编辑器。
- [当前 DOCX 修订契约](https://github.com/xuzhougeng/wisp-science/blob/main/docs/docx-revisions.md) 已有源文件 SHA-256、段落 ID、原文唯一匹配、生成新的 DOCX 修订副本，以及单条 / 按类型接受或拒绝。修订写入原生 OOXML；审阅保存有备份与冲突检查。可评估复用这些 Rust 文档处理契约和离线测试思路。
- 已有实现主要支持 Transitional DOCX 的普通顶层正文段落；表格、公式、域、链接、绘图、已有修订及跨段落保护范围等具有明确只读限制。#1706 的工具选择仍属提示引导，shell / Python 等路径仍可能绕过，不能据此宣称已经强制保护所有写入。

### 两种文稿入口与分级兼容

| 入口 / 级别 | 用户可见行为 | 保存边界 |
| --- | --- | --- |
| 新建标准稿件 | 使用 WispPaper 支持的标题、段落、列表、图表与引用结构；按模板和测试结果逐步扩展 | 按已声明的能力生成 DOCX；不承诺任意 Word 模板的分页一致 |
| 已有 DOCX：可编辑 | 导入时列出经验证可安全编辑的段落和操作；首版优先普通正文文字替换，再逐项增加样式、结构编辑 | 仅修改确认支持的节点，保留无关部件；每项操作都应有回写验证 |
| 已有 DOCX：只读保留 | 对暂不能安全编辑的公式、复杂表格、引文域、浮动对象等显示只读对象或明确占位，允许在其外部的安全范围编辑 | 连同 OOXML、关系与资源保留；跨段落域、书签或批注等必要时锁住整个影响范围 |
| 无法安全处理 | 明确说明限制，提供 Word 等外部编辑入口；必要时将整个文件设为只读 | 不声称可无损回写，不通过重新生成整篇文档绕过限制 |

导入弹出「兼容性卡片」，按当前文件列出可编辑、只读保留、无法安全处理的内容及原因。导出前再次检查并显示变更与限制；用户能明确知道这份文件适合在内置编辑器完成哪些工作。

### 内部文档模型、OOXML 与 DOCX 各司其职

- 结构化文档模型（可序列化为 JSON）承载编辑状态、段落身份、选区、引用及撤销；它本身不是保真承诺。不要把 DOCX 简化成 Markdown 或普通文本再重建后称为兼容。
- 保留原始 DOCX 包及 OOXML 部件、关系、样式、编号和媒体；为可编辑节点建立到源文件版本的映射，通过受限补丁回写。不能只保存主 XML，或只因 ZIP 中其他文件未变，就认定布局和语义没有变化。
- DOCX 作为交付及与 Word 交接的格式；修改文字后允许正常重排，但应明确不保证逐页一致。原生修订、编辑器内部建议和已接受正文之间需要定义可测试的转换。
- 技术选型同时评估成熟文档引擎和受限原生编辑方案的许可证、离线能力、打包体积及平台支持。WispPaper 是 Rust / GPUI；Web 编辑器不能默认直接嵌入，避免为这一概念强制引入浏览器内核、Python 或独立服务。

### 实时辅助与 AI 修改如何落地

建议工作区是「左侧文献 / 大纲，中间稿件，右侧助手 / 修订」，核对时在当前工作区查看 PDF，保留稿件位置和对话。用户直接编辑支持范围内的内容；AI 默认先生成建议，展示删除、插入或成对改写，可逐条接受 / 拒绝或按类型处理，支持撤销。

- 自动保存的是可恢复工作草稿，和覆盖用户导入的原始 DOCX 分开。初次保存默认生成可审阅副本 / 另存为；后续保存当前工作副本时检查版本、保留备份并采用临时文件替换，发现外部修改则要求重新读取或处理冲突。
- 用户可显式选择自动应用某类低风险修改，但必须可撤回并遵守同一兼容性与来源检查；不能让助手通过脚本重建、覆盖文件来绕过审阅。
- 写作 Skill 可约束术语、章节范式、谨慎表述、引文和证据检查，并沿用 2.1 节的 wisp-science Skill 格式。文档写入权限、受保护范围、冲突和原文匹配由程序校验，不能仅靠 Skill。
- 将用户手改、AI 建议和已接受修改区分记录；AI 建议绑定稿件版本、目标段落及必要的证据。段落变动后重新定位或失效，避免将旧建议套到新正文。

### 公式与复杂对象：分别声明读取、显示、编辑、保留和导出能力

「支持公式」至少要拆成上述五项。首版可将未支持编辑的 OMML 公式作为只读对象保留，并允许在经验证安全的相邻文字范围修改；无法正确显示时明确标记并提供外部预览。LaTeX 输入与 OMML 转换后续逐项验证，不能承诺任意公式双向无损。不得静默删除公式或转成图片后仍宣称保留可编辑公式。

同样检查复杂表格、Zotero / EndNote 等引文域、交叉引用、脚注尾注、页眉页脚、分节、浮动图片和已有修订。保留域不等于能更新域；内置编辑器自管的参考文献与外部引文管理器字段应明确区分。

### 分阶段交付与验收

1. 先建立已有 DOCX 的兼容性报告、只读预览与版本身份；用户打开文件就知道可处理范围。
2. 再交付普通正文的一条完整流程：「选中文字 → AI 原生修订副本 → 逐条接受 / 拒绝 → Word 复查」，复用 #1679 / #1706 的经验，但不默认已有全部实现。
3. 然后增加支持范围内的用户直接编辑、草稿恢复、撤销、引用 / 证据插入与新建稿件导出；公式和表格编辑分别另立可验收能力。

以包含格式化文字、公式、表格、引文域、图片、页眉页脚和既有修订的固定样例逐项回归。区分 ZIP / XML 有效性、未修改部件保留、公式与域语义、审阅结果和 Word 实际打开 / 往返检查；验证不支持内容不会静默丢失、拒绝修订可还原原文、过期建议被阻止、原件保持不变。日常自动化测试不要求安装 Word，实际 Word 兼容性另行记录验证结果。

本节纳入 #29 总构想，后续再按维护者认可的范围拆小 issue / PR；不预设仓库合并，也不因提出编辑器就改变当前本地优先的产品约束。

## 2.4. 讨论：AI 味防御机制与可配置的写作风格 Skill

建议在写作流程中增加一层「AI 味防御」，面向模型起草、润色、翻译及章节整合后容易出现的模板化表达。目标是让论文更具体、自然、简洁，符合研究者本人的表达方式和目标领域的写作习惯。此处先提出概念和接口，具体 Skill 内容由提出者后续补充；尚未形成已采纳的实现计划。

### 希望改善的写作问题

- 空泛套话、宣传性措辞、缺少具体对象的宏大结论，以及过度使用强调词。
- 机械重复的过渡句、段落开头和总结句；每段都使用相同的论述模板。
- 句子冗长、名词堆叠、同义反复，或为显得正式而引入不必要的复杂表达。
- 泛泛而谈，未交代实际方法、适用条件、比较对象、结果和局限。
- 润色后抹去作者原有语气，或让不同章节呈现不一致的术语、时态与论述强度。

不将某个词或句式一律判定为“AI 生成”。判断应结合语境、章节用途、学科惯例和作者偏好；不通过故意加入错误、打乱语法或机械替换同义词来获得所谓“人类感”。

### 预留用户后续补充的 Skill

沿用 2.1 节与 wisp-science 兼容的 Skill 包格式，允许用户导入、编辑和版本化自己的风格约束，不另造一套不兼容的文件格式。后续 Skill 可包含适用语言、论文类型与章节、偏好及避免的表达、带理由的正反例、作者提供的写作样例和检查步骤；这些是待讨论内容，不预设为新的必填 schema 字段。

支持按项目或当前稿件选用，并明确本次修改实际加载的 Skill 版本。用户未配置 Skill 时，仍可正常写作；不能把尚未提供的 Skill 标为已启用或已完成检查。中英文与不同学科应分别校准，避免把一种风格套到所有论文上。

### 建议交互：检查问题、解释原因、按需改写

在编辑器提供「检查 AI 味 / 写作风格」入口，也可在生成段落后按需运行。展示被标记的具体片段、触发的 Skill 规则、修改理由及候选改写，让用户逐条接受、拒绝或忽略；保留原文、差异及撤销。自动检查可以给出建议，不默认自动重写整篇稿件。

用户可限定只检查选中文本、某一章节或全稿，并区分“仅检查”和“提出修改”。采用论文范式或写作样例时，学习组织方式和表达偏好，避免复制原文。检查结果应引用具体规则与上下文，不只给出一个缺少依据的“AI 味分数”。

### 具体 Skill 规则：论断与支持引文紧邻、范围清楚

补充一项“AI 书写语言与引文要求”的具体约束：模型常先写若干论断、例子或比较，再在句末 / 段末集中放一串引用，读者难以判断每篇文献究竟支持哪一项。建议将“论断—引文对应清晰”纳入写作 / 润色 Skill 的检查规则；它同时涉及表达与证据归属，不能仅按“AI 味”或引文数量评判。

**脱敏说明**：以下仅保留反馈中的一般结构问题，示例完全虚构；不上传原截图，不沿用原稿的研究主题、专有名词、语句、作者信息、文献编号或可识别项目细节。示例引文键仅为说明位置的占位，不代表真实文献，不能带入正式稿件。

#### 写作与改写要求

- 先识别每项需要外部证据的具体论断，再把支持它的引文放在对应分句 / 句子的就近位置。“紧邻”指支持范围明确，不是固定字符数或视觉上的距离；标点前后、上标 / 作者年份等形式服从目标期刊与所选样式。
- 同一句有多个不同论断，且分别来自不同来源时，在各自分句处引用，或拆成短句。不要把几篇文献堆到长句 / 段末，让人误以为它们共同支持前面所有内容。
- 同一论断确由多篇文献支持时可以合并引用；连续表述来自同一来源且归属清楚时不机械逐句重复。作者在句首的明确归属也可成立，不能只因文末没有括号就判错。
- 综述段落的总括句与具体例子分别检查。支持某个例子的文献不能自动支撑整段的普遍性结论；“均”“主要”“首次”“尚无研究”“显著优于”等扩大范围或加强语气的措辞，须有对应依据。材料不足时缩小表述或标记待补证据，不能靠移动引用制造支持。
- 改写、拆句、合句、翻译或删减时，让原有引用跟随其实际支持的论断；保持引文身份、页码 / 定位和科学含义。需要换来源时单独提出，不为改善位置而新增、删除或猜测文献。
- 区分文献事实、作者解释、研究假设和本项目结果。未经检索支持的推断要明确表达；自己的结果可回溯实际结果 / 图表，不强行给每句话配外部引用。

#### 虚构的通用正反例

范围不清的写法：

> 算法甲在条件 A 下提高了指标 X，工具乙减少了操作步骤，两者也都适用于其他场景 [@source_a; @source_b]。

只有在核对后确认“source_a 支持第一项、source_b 支持第二项，二者均未验证其他场景”时，可建议：

> 在条件 A 下，算法甲提高了指标 X [@source_a]。工具乙减少了所报告任务中的操作步骤 [@source_b]。这些材料尚不能支持对其他场景的推广。

此例用于展示拆分与限定支持范围，不表示实际存在这两篇论文。最后一句也只是对所检查材料范围的说明，不能扩写成“整个领域尚无相关研究”。

#### 检查卡片与输出

按“待检查片段 → 具体论断 → 当前引文及来源位置 → 存在的对应问题 → 建议修改 → 仍待核实项”展示。建议区分“位置 / 归属不清”“引文缺失”“来源只支持部分内容”“尚未读取来源，无法判断”，不把形式错误和科学支持判断混成一个通过标记。

用户可仅检查选中段落，也可检查一节或全稿；先给差异与理由，再逐项接受 / 拒绝，保留原文和撤销。没有读取到原文时可以指出位置歧义，但不得声称已经验证引文支持关系。程序可辅助识别引用标记、分句与改写后的引用丢失，语义支持仍需结合原文和作者核对。

#### 接入与验收边界

作为后续 Skill 的明确规则，也可按 #40 的轻量自定义斜杠模板思路提供“检查论断与引文”入口；复杂 Skill 执行仍可放在 wisp-science / 外部助手，不由此要求 WispPaper 内置运行时。与 #28 的原文定位 / 逐字匹配衔接：摘录能匹配到原文不等于它支持该论断。引用格式化 / BibTeX 导出通过，也不等于论断—文献对应已核实。

固定脱敏样例至少覆盖：不同来源的多分句、段末集中引用、同一来源的连续表述、多来源共同支持、叙述式引文、中文 / 英文与不同引用样式、作者自身结果，以及改写后引用是否跟随。没有原文的样例只评估位置与归属，不给语义支持的成功记录；“无须改动”的合理写法也应保留，避免为追求紧邻而过度拆句和重复引用。

### 风格修改的边界

- 风格建议必须保留研究事实、数值、单位、统计量、公式、术语、引用及证据关联。不能为了语言自然而编造细节、扩大创新性、强化因果关系或隐去局限。
- 风格规则与事实、证据或学术表达要求冲突时，保留事实并提示冲突；涉及科学含义变化的建议单独标记，不混入纯语言润色。
- 与 2.3 节审阅机制共用稿件版本、修订及接受 / 拒绝流程。程序可检查数值、引用和受保护对象是否发生变化；语义是否保持仍需作者审阅，Skill 不能代替科学判断。
- 本机制评价表达质量，不判定作者身份，也不承诺通过任何 AI 文本检测器。AI 使用披露仍按目标期刊或机构要求处理。

### 后续讨论与验收建议

先由用户补充一版 Skill 和代表性样例，再验证一个最小流程：「选择段落 → 加载指定 Skill → 列出风格问题与理由 → 提出修订 → 用户选择 → 保存可撤销结果」。检查已知模板化表达能否合理改进，以及本来合适的学术表达是否被误报；比较修改前后的可读性、作者偏好和事实保持情况。

以固定中英文样例覆盖规则冲突、未加载 Skill、数字 / 引文保护、版本变化和拒绝还原；将作者的接受 / 拒绝反馈用于后续调整，未经用户选择不自动改写 Skill。自动测试侧重流程与可验证的不变量，风格效果由人工样例评审，不以第三方 AI 检测分数作为验收承诺。

## 2.5. 讨论：自定义模型驱动的机制图 / 流程图，以卡片向导交付可编辑 PPTX

当前本帖只概括提到 ScientificFigureLibrary 的模板与图形复用，尚未定义「论文内容 → 模型识别 → 机制图 Skill / 流程图 Skill → 可编辑图形 → 图注与稿件」的完整流程。建议新增这一扩展构想，后续在范围确认后拆为小 PR；本节不表示现有代码已经支持，也不代表维护者已经接受或排期。

### 目标与模型配置

允许用户基于单篇 / 多篇论文、选中原文、问答结果、阅读笔记或当前稿件中的实际结果，表达绘图意图，例如“把这段方法画成流程图”“将已核实的调控关系画成机制图”，经确认后生成可继续修改的图形。

用户可选择已有模型配置，或设置绘图任务使用的自定义模型，包括服务提供方 / 接口、模型 ID 与连接配置。文本理解、视觉理解、图形规划 / 生成可以按能力选用同一模型或不同模型，不强制绑定某家服务，也不要求所有模型都具备图像输出能力。

- 明确区分“理解论文和输出图形结构的模型”“可选的图像生成模型”与“生成 PPTX 的确定性工具”。仅能返回图片的模型不能独自满足可编辑交付要求；缺少必要能力时提示限制，保留用户手动调整图形结构的入口。
- 调用前展示将发送的论文片段 / 页面和服务身份，允许用户缩小范围；不默认上传整个文献库。凭据使用既有秘密存储方式，不写进稿件、图形文件、提示词快照或导出包。
- 记录实际模型、配置版本、生成状态与失败原因；模型识别结果是待确认建议，不自动成为已经核实的科学事实。

### 卡片式交互

每一步展示输入依据、候选结果、可编辑字段与待确认内容；支持返回修改、保存草稿、取消和断点继续。

| 卡片 | 交互与处理 | 保存产物 |
| --- | --- | --- |
| 1. 意图与来源定位 | 用户选择画机制图还是流程图，也可由模型提出建议；识别要表达的对象、受众、细节层级和语言。按意图检索论文中的相关方法 / Results / 图注，展示具体文件、页码与片段，由用户选择材料 | 经确认的绘图目标、来源范围与定位 |
| 2. 模型与 Skill | 选择 / 配置自定义模型，检查其文本、视觉与结构化输出能力；选择机制图 Skill 或流程图 Skill，预览规则、模板、资源与依赖 | 模型选择、Skill 来源 / 版本、能力检查结果 |
| 3. 结构与证据 | 机制图先给出实体、关系、方向、作用类型和证据；流程图先给出步骤、输入输出、判断、分支与顺序。用户增删节点、改文字、调整连线，确认后才推进 | 可编辑的节点 / 连线结构、证据关联和未确认项 |
| 4. 布局与预览 | 选择布局、画布比例、字体、字号、配色和图例；预览后局部修改并生成默认 PPTX | PPTX、可选预览、用于重建的结构化源文件 |
| 5. 保存与插入位置 | 推荐稿件中的章节 / 段落位置，解释推荐依据并显示上下文；用户确认插入位置，或仅保存到独立图形子文件夹 | 文件路径、图形身份 / 版本、可选稿件关联 |
| 6. 是否写图注 | 明确询问“是否生成图注并更新到稿件编辑器？”；可选不生成、仅生成草稿、生成并在确认后插入。预览图注与引用后由用户确认 | 图注草稿 / 已接受版本、图号及稿件关联 |

“定位来源论文中的相关位置”和“确定用户稿件中的插入位置”分别处理。模型可给出候选，不直接猜测或移动用户光标；找不到可靠来源或合适插入点时保留未定位状态，支持用户指定。论文定位可复用已有 PDF 页码与原文回跳；稿件插入需要单独的章节 / 段落身份，不能拿 PDF 页码替代。

### 默认交付可编辑 PPTX

PPTX 是默认交付格式。文字使用文本框，流程框、箭头、连接线、分组及适合的机制元素尽可能使用原生 PowerPoint 对象；用户应能修改字体、字号、文字、颜色、位置、尺寸和连线关系。保留结构化源文件，便于局部再生成与审阅。

不能只把一张 PNG / JPEG 放入 PPTX 就标为“可编辑”。确需栅格图片或无法拆解的素材时，明确标注其可编辑粒度与替换限制；SVG 放入 PPTX 也不自动等于所有内部元素都能逐项编辑。素材须记录来源和使用许可，不直接复制论文原图并当作新生成图。

WispPaper 中可先做图形卡片、预览和文件关联，不预设内置完整 PowerPoint 编辑器。细节可在 PowerPoint / LibreOffice 等外部工具中修改；外部修改后重新关联 / 刷新，保留版本和冲突检查。外部 PPTX 修改自动同步回结构化源模型并非首版承诺，重新生成前应提示可能影响手工修改，另存新版本。

### 图注、编辑器与文件管理

- 支持与当前稿件编辑器交互；也支持独立保存，默认不改原始 PDF。示例目录为当前项目内的 `figures/<figure-id>/`，按版本保留 PPTX、结构源文件、预览、来源记录和可选图注；具体目录可由用户选择。
- 图形、图注和稿件分别有身份与版本。插入编辑器的是受支持的预览 / 附件链接、图形关联和可编辑图注，不把静态预览等同于 PPTX 全元素编辑。首版允许手动导入外部生成的图和图注。
- 图注说明图的内容、节点 / 箭头 / 颜色含义、必要条件与局限，分别引用相应来源；区分原文报道、用户实际结果和假设示意，不补造实验或数值。用户选择不写图注时，仍可交付 PPTX。
- 生成与插入分开确认；写回前显示目标位置和差异，保存可撤销结果。不覆盖现有图注或正文，稿件版本变化时重新定位 / 确认；图号和交叉引用须按编辑器实际支持范围检查，不能只改显示文字就宣称全稿已同步。
- 后续图形结构改变时标记图注可能需要复核，保留用户修改；不默认用模型重新生成的图注覆盖人工内容。

### 科学与实现边界

1. **机制图的事实边界**：每条关键关系关联原文或实际证据。相关性不画成已证实因果，不从通路常识自动补出论文未证明的关系；推断和假设使用清晰图例并保留待核实标记。多篇论文或模型输出的综合图明确说明各自来源，问答文本本身不等于原始证据。
2. **流程图的范围边界**：区分论文描述的方法、代码已实现的步骤、实际运行过的步骤与未来计划，不把拟议流程画成已执行实验。用户确认的结构和顺序优先于未经核实的模型推断。
3. **Skill 与工具边界**：机制图 Skill / 流程图 Skill 负责组织、风格与核对步骤，PPTX 生成器负责实际对象与文件；程序验证结构及文件产物。Skill 存在、模型返回成功或预览显示正常，都不等于可编辑文件已生成并验证。
4. **现有产品边界**：维护者在 [本帖回复](https://github.com/xuzhougeng/WispPaper/issues/29#issuecomment-6795898638) 中明确不在 WispPaper 引入 Skill 运行时，复杂工具编排放在 wisp-science。对此，本构想优先讨论清晰的交接方式：WispPaper 负责来源选择、定位、绘图意图与图 / 图注关联；Skill 调用和 PPTX 生成可由 wisp-science 或外部工具完成，再导入结果。若以后讨论内置执行，须单独说明依赖、接口及产品边界变化，不能将本节视为推翻维护者结论。
5. **能力复用边界**：可评估 ScientificFigureLibrary 的模板、资源和版本接口；机制图 / 流程图需求需单独验证，不宣称现有图形库已具备这整套能力。也不将这项“创作自己的图”与 #24 中暂不排期的“提取 / 保存论文图片”混为同一需求。

### 后续 PR 拆分与验收建议

建议按“图形任务与来源契约 → 结构确认卡片 → 一种图的可编辑 PPTX 导出 → 文件 / 编辑器关联 → 可选图注写回”分步交付，机制图和流程图可分别验证；自定义模型配置优先复用既有配置入口。先完成外部生成 / 手动导入的一条闭环，再按维护者认可的范围增加自动连接，不要求一次实现全部卡片与执行能力。

验收使用固定材料、假模型 / 假工具，不依赖真实 API Key 或付费服务；检查来源位置与证据状态、结构编辑与任务恢复、取消 / 失败后的文件状态、目录版本和稿件冲突。对 PPTX 同时做包结构检查与实际打开检查，抽样修改字体、文字、节点和连接线；另验图注的“不生成 / 仅草稿 / 确认插入”、撤销与版本变化。截图正确不代替可编辑性验证，文件有效不代替科学内容核验。

## 5. 最需要统一的是来源与证据关联

建议先定义最小的数据契约，而非立即建立庞大的新架构：

- 文献与具体文件：区分同一篇论文的主文、补充材料与文件版本。
- GitHub 仓库来源：保留仓库 URL、明确 commit、文件路径与行定位，并记录实际使用的内容。
- MCP 运行与结果来源：保留服务器 / 工具身份、任务 ID、参数、数据与环境版本、状态及产物定位；与稿件论断绑定。
- 摘录与批注：保留原文、文件标识、页码、定位信息及用户说明。
- 文章总结：区分模型生成和用户编辑，记录所依据材料与覆盖范围。
- 论断与证据：保存支持、反对、局限及核验状态。
- 稿件与引用：段落或章节引用稳定的文献 / 证据标识，不能直接把对话中的 P1/P2 当作跨稿件引用键。
- 文档与修订：记录源 DOCX 校验值、工作副本、编辑器模型版本、段落映射、兼容性报告及修订 / 备份身份；建议只对绑定的版本有效，保留原生对象与证据关联。
- 自有图形与图注：记录图形身份、PPTX / 结构源版本、模型 / Skill / 模板身份、节点关系的证据、图注版本与稿件目标位置；凭据不进入这些记录，外部手改与重新生成需识别版本差异。

由此让「点击论断 → 查看摘录 → 返回原始 PDF」成为可保存、可恢复的关联。历史对话、总结和稿件应复用同一来源身份；源文件变化时重新校验或提示失效。

程序匹配原文与科学判断需要分别展示：全文匹配、部分匹配、无法定位，不等于该原文足以支持论断。核对 Skill 或提示模板约束步骤，程序校验负责可验证的边界。

### 总索引维护规则

本帖作为整体构想、需求边界和关联关系的总索引；具体实现与验收仍在对应 issue / PR 中讨论，产品决策与合并由维护者决定。

- **全量纳入**：开放和已关闭 issue 都保留编号、链接、概念归属、状态和范围约束。关闭后不从索引删除；重复、合并、暂不计划或部分交付，应记录实际原因与后续去向。
- **状态与能力分开**：OPEN 不等于完全未实现，CLOSED 不等于已完整交付。实现进度以可核对的 PR、合并提交与验证结果为依据；不因已有部分基础就宣称整条需求完成。
- **同步维护**：后续新增 issue、实质修改范围、评论确认已有功能，或关闭 / 重开时，同步更新本帖对应条目。此处为本讨论的维护约定，状态表是注明日期的快照，不是自动同步服务。
- **保护已有能力边界**：文献库 / 单篇问答、历史保存、出处卡片跳页高亮、手动笔记等已经存在。需求应说明在这些能力上补什么，不重复写成从零新增。
- **共用来源与证据约束**：文件导入、PDF 下载、文字可读、实际提供给模型、原文匹配和论断得到支持分别表达；引用、笔记、图片和稿件共用稳定的文献 / 文件身份与来源定位。
- **小步交付**：跨仓库融合按适配器、数据对象或单项行为拆分，不把概念讨论当成一次合并全部仓库的实施承诺。关联 issue 可以合并处理，但需保留范围对应与未完成项。

## 7. 建议的交付顺序

以下保留整体构想的历史建议；当前实际交付与维护者已确认的产品分工以上方进度、索引和评论为准，未接受项需先确认归属，不能当作已承诺的 WispPaper 内置路线图。

1. **全文获取与可靠读取**：分步交付一种来源的批量 PDF 查找 / 下载关联，以及解析、覆盖率、诊断、进度和缩放。基础下载不依赖模型；助手辅助查找后续作为可选增强接入，用固定样本验证各阶段结果。
2. **阅读成果沉淀**：保存批注 / 摘录，并打通选中原文、追问、回跳。先交付一条可持久恢复的摘录，再扩展管理界面。
3. **总结与证据关联**：文章总结、跨论文比较和逐条核对共享来源身份；先完成一种结构化总结。
4. **完善写作基础并评估内置编辑器**：基于 PR #31 补齐稳定来源、证据核对、版本与 Markdown + BibTeX 导出；2.3 节另按兼容性报告、普通正文修订副本与审阅、受限直接编辑、新建稿件导出逐步验证，复用 wisp-science 的契约经验，不一次实现完整 Word。
5. **GitHub-to-Paper 最小版本**：复用前述证据和稿件基础，以卡片向导打通 README 定位、方向确认、Web Search 范式、创新点、兼容 Skill 和基于已有证据的 Results 初稿；仓库接入、MCP 客户端、Skill 兼容与各阶段分别小步交付。
6. **按需求扩展与确认边界**：远程实验、CSL 格式、Word / LaTeX 导出、更丰富的图表与多服务器协作分别讨论外部交接和产品归属；2.5 节机制图 / 流程图先验证来源契约、结构确认、可编辑 PPTX、文件关联和可选图注写回，不将这些讨论列为维护者已经采纳的内置计划。

每个 PR 增加一种持久对象、一个解析适配器或一项可验收行为，保持向后兼容、本地优先和独立文献库的可迁移性。

**1. 「本地、证据可追溯的文献研究与写作工作台」是否符合长期方向？**

符合。Wisp Paper 的主线就是 检索 → 筛选 → 阅读 → 提问 → 写作，每一步的结论都能回到原文的某一页。「证据可追溯」我理解为两条硬规则：模型的说法必须带出处，出处由程序去原文里找；收录与否、证据够不够，由人决定。

**2. 第一阶段是否优先「可靠读 PDF → 保存摘录 → 问答核对 → 一键回原文」？**

是，顺序也基本照你说的：

- 0.3.0：可靠读取和反馈（#17、#22、#26，新读取器已在 main 上），阅读体验（#18、#27），以及 #21、#30。

**3. 写作：内置面板，还是通过 Markdown / BibTeX 交给外部编辑器？**

内置，而且已经在 main 上了（#31「写作」页，随 0.3.0 发布），不过思路和你设想的不一样，值得说明：它不让模型替你写段落。稿子按 摘要 / 导言 / 方法 / 结果 / 讨论 分部分写，旁边是库里论文**同一部分**的句子，按你正在写的这段话排序；可以在光标处插入引用，或跳到这句话在 PDF 里的位置。前提是把每篇 PDF 按版面读出来并分好节，#31 的大部分工作在这里。

下一步是导出：Markdown 加 BibTeX。Word、LaTeX 排版和 CSL 格式不做，交给外部工具。

**4. 其他仓库的能力，哪些抽成共享组件，哪些只复用设计？**

只复用设计，不共享组件。几个仓库的技术栈各不相同（Rust + GPUI、Go + Web、Tauri），能共享的只有数据格式和接口。接口已经有了：`wisp mcp` 把文献库作为 MCP 服务开放出去（检索、读全文、按部分找句子等），wisp-science 或任何支持 MCP 的助手今天就可以把 Wisp Paper 的库当作文献来源。这就是我想保持的边界。CiteBox 的部分见 #24。

**5. 是否支持 GitHub-to-Paper 作为第二条入口？**

不在 Wisp Paper 里做。原因不是这个想法不好，而是它需要的东西（读仓库、连接外部 MCP 服务器、跑实验、管理运行结果和版本、Skill 运行时）加起来是一个科研计算工作台，那是 wisp-science 的位置。放进来会让一个「文献库」变成两个产品。

Wisp Paper 在这条路线里的角色是供给文献一侧的证据：相关工作检索、原文引用、同类论文的 Results 怎么写（`find_sentences` 做的正是「看别人这一部分怎么写」）。建议把 GitHub-to-Paper 的向导提到 wisp-science，那边通过 MCP 调用这里。

**6. 写作 Skill 是否以 wisp-science 的包格式为兼容基准？**

Wisp Paper 不引入 Skill 运行时（脚本 sidecar、Python / R 依赖都和「单文件、无运行时依赖」冲突）。这里对应的东西是斜杠命令：`/search`、`/cite`、`/review`、`/compare`、`/write` 都是提示模板。可以考虑的是**用户自定义的斜杠命令**（自己写一段模板，起个名字），这很轻，如果你觉得有用，欢迎单开一条。

**7. 仓库分析、MCP 读取已有结果与远程实验的边界？**

同第 5 点：都在 wisp-science 一侧。Wisp Paper 只负责文献，并保证给出去的每条摘录都带文献、文件和页码。
